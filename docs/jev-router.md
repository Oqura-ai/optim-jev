# jev-router

![jev-router](../assets/jev-router.png)

With routing on, Claude makes every file change through a subagent, and each subagent runs on the right model for its task, within rules you control. The rules evolve: when your preferences change, Claude updates them.

## Rules

Two files in `.optim-jev/jev_router/`, both meant to be committed:

| File | Holds | Enforced? |
|---|---|---|
| `rules.json` | anything tied to a **path**: which models may write or delete there, and what the area is | yes, every write is checked |
| `RULES.md` | facts **no path rule can express**: kinds of work ("docs only by sonnet or cheaper"), hidden coupling, invariants | no, shown to Jev and the subagent as guidance |

They never repeat each other.

```json
{
  "schema": 1,
  "paths": {
    "src/core/": { "write": ["sonnet", "opus"], "why": "pricing engine; subtle invariants" },
    "src/gen/":  { "min": "none", "why": "generated by protoc" },
    "docs/":     { "why": "guides and examples" }
  }
}
```

- `write` lists the models allowed; `"min": "sonnet"` means sonnet and everything stronger; `"min": "none"` blocks every model.
- `delete` defaults to `write`.
- A path takes the rule of its nearest listed ancestor. A path under no rule is open to every model.

```markdown
## General
- Documentation work only by sonnet or cheaper.

## src/core/
- Prices are integer cents; never floats.
```

`## General` facts go with every task; a `## <path>` section only when a file under it is edited.

## Setup: `/jev-route init`

1. **Scan**: the project tree to depth 2, plus a digest of the main files (first comment and top-level names, never contents).
2. **Check models**: one tiny call per model to see which your account can use; saved to `models.json`.
3. **Draft**: a Claude model (default sonnet) writes the scopes and facts. Every scope is open to every model unless your directive says otherwise.
4. **Save**: `rules.json` and `RULES.md`; facts that repeat a rule are dropped. Routing turns on.

If rules already exist, init refuses unless you pass `--force` (the old files are kept as `*.bak`).

## Evolving the rules

The routing section of the system prompt tells Claude how to maintain both files. When you say "let haiku write the tests", Claude edits `rules.json` itself:

- The main loop may write **only** these two files; every other write still goes through subagents.
- After each edit the rules are reloaded, so enforcement matches immediately.
- `rules.json` is re-validated: bad JSON, unknown model names or ignored entries produce a toast for you and a message back to Claude.
- Claude is told never to change a rule just to get past a refused write.

## A routed subagent, step by step

1. **Spawn**: Claude starts a subagent with a task. The router finds the project paths its prompt names.
2. **Allowed models**: the models every named file's rule allows (if they conflict, the strongest any allows). With the cap on, nothing above the session's model.
3. **Pick**: one model allowed → used directly. Several → Jev picks the least capable one that will do it correctly, given each file's `why` and the relevant `RULES.md` facts. Jev failing → the session model if allowed, else the strongest allowed.
4. **Brief**: the subagent's prompt gets the rules and facts for its files, and the files it must never edit.
5. **Guard**: every write and delete is checked against `rules.json` for the subagent's model. A refused write names the rule.
6. **Escalate**: after 3 failed writes in one subagent, the next subagent for those files starts one model up. The running one isn't switched.

## Known gaps

- Shell deletes and moves are detected by pattern (`rm`, `mv`, `del`, …), best effort only.
- `RULES.md` steers but doesn't enforce.
- Claude could still loosen a rule to get unblocked; only the instruction prevents it.
